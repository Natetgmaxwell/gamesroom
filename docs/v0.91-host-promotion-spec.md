# V0.91 — Host promotion + multi-host

## Problem

Games Room has always been single-host: the creator is the host, the
host role is set on room creation (migration 004 trigger), and the only
way to change who hosted a room was "delete the room and create a new
one" — which destroys the room's history.

User feedback (2026-08-25, kanban t_ba6b9ca5): *"now lets work on how I
promote a normal member of a room to a host?"*

The current data model already supports multi-host (the `Member.role`
column is a free `text NOT NULL` with a `role IN ('host','member')`
check — nothing prevents two rows from holding `'host'`). The
restriction was purely application-side: no RPC, no service function,
no UI affordance. This slice closes all three.

## Design

### Decisions (locked)

- **Promote-and-demote + multi-host.** Any host can promote any
  member to host. Any host can demote any host back to member. A room
  can have multiple hosts; a room must always have **≥1** host. No
  `.cohost` / `.moderator` middle tier** — keep the `RoomRole` enum
  two-case.
- **`RoomRole` enum stays two-case** (`.host | .member`); multi-host
  is achieved by allowing >1 `role = 'host'` row in
  `room_memberships`. No schema migration on the column.
- **`Room.userRole`** stays read-only from iOS (server-set). No model
  change to `Room.swift`.
- **Single RPC, not two.** `transfer_host_role(p_room_id,
  p_target_user_id, p_action)` with `p_action` ∈ `{'promote',
  'demote'}`. Cleaner than two separate RPCs; one auth path, one
  return shape.
- **No max-host cap.** A host can promote unlimited members. The data
  model doesn't constrain it; the UI is the soft gate. (Could be
  added later as `p_max_hosts` parameter — deferred.)
- **Caller's own row has no menu.** A host can't accidentally
  self-promote (no-op) or self-demote (would leave the room hostless
  in single-host rooms); the context menu is suppressed for the row
  matching the caller's `userId`.

### Workflow

1. Host opens **Settings → Members** in any room they host.
2. Each roster row gains a context menu (long-press on iOS, right-click
   on iPad):
   - Member row → **"Make host"**
   - Host row (not self) → **"Demote to member"** (destructive role)
3. Tapping a menu item fires a confirmation alert:
   - Promote → *"Make Alex host? You'll both have host powers. You can
     demote them later."* Buttons: **Cancel** | **Make host**.
   - Demote → *"Demote Alex? They'll lose host tools. The room will
     still have you."* Buttons: **Cancel** | **Demote** (destructive).
4. On confirm: the iOS service calls `transfer_host_role`. The server
   flips `room_memberships.role` and returns the full roster. The
   client rebuilds the members cache from the authoritative set; the
   roster re-renders immediately with the new role badges.
5. On the error path (e.g. last-host on a single-host room): the
   sheet-level alert shows the typed error message ("A room must
   always have at least one host."), no state change.

### Edge cases (server-enforced)

- **Promote a member** → idempotent: setting `role = 'host'` on a
  row that's already `'host'` is a no-op (the WHERE clause excludes
  the same-value write so `updated_at` doesn't bump spuriously).
- **Demote the last host** → RPC raises `last_host` with errcode
  `P0001`. UI surfaces it inline.
- **Non-host caller** → RPC raises `not_authorized` with errcode
  `42501`. (Defense in depth: iOS already gates on `room.userRole`,
  but the server is the authority.)
- **Target not in this room** → RPC raises `not_found` with errcode
  `P0002`.
- **`p_action` not in `{'promote','demote'}`** → RPC raises
  `invalid_action` with errcode `22023`.

## RPC contract

```sql
public.transfer_host_role(
  p_room_id        uuid,
  p_target_user_id uuid,
  p_action         text  -- 'promote' | 'demote'
) returns setof public.room_memberships
```

- `SECURITY DEFINER`, `set search_path = ''` (locked search_path
  per the project's SECURITY DEFINER convention).
- Auth check first: caller must have `room_memberships.role = 'host'`
  in `p_room_id`. Multi-host inheritance: any host (not just the
  creator) can promote/demote.
- Returns the full room roster so the iOS client rebuilds its
  `membersByRoom[roomId]` cache from one round-trip.

## Acceptance criteria

1. **Migration 091** exists, applies cleanly to local Supabase, and
   the `transfer_host_role` RPC passes all spec'd edge cases.
2. **iOS service function `RoomService.transferHostRole(...)`**
   exists, calls the new RPC, returns the updated roster, updates the
   local cache, and maps RPC error strings to typed `HostRoleTransferError`.
3. **`RoomSettingsMembersSheet.memberRow`** shows the context menu
   per member row when the caller is a host and is not viewing their
   own row. Action label matches the member's current role.
4. **Confirmation alerts** fire before either action.
5. **Error handling** surfaces `lastHost` (and other typed errors)
   inline without state change.
6. **Mascot test runner is green**: `./build-and-run-tests.sh`
   → 257/257 passing.
7. **Parse-check is green**: `./scripts/parse-check-swiftui.sh` →
   52/52 passing.
8. **No regressions**: all existing host-only flows still work
   (Tonight's Star picker, room settings, host score entry, etc.).
   Multi-host means: if the caller is the new host, they see host
   chrome immediately on next `refresh()`.
9. **No new design tokens**: reuse existing colors / fonts / spacing.
10. **No banned words** in new UI copy.

## What's NOT in scope (locked)

- No `.cohost` or `.moderator` role.
- No "leave room as host" UI — the doc says "ask another host to
  demote you." If the host wants to leave, they delete the room or
  get demoted by another host.
- No re-capture of the App Store screenshots — the screenshot set in
  `screenshots/upload/` is independent of this change (post-V0.97
  submission cycle).
- No `Theme.Palette` / `Theme.Typography` / `Theme.Layout` changes.
- No new RPC name. Single RPC + `p_action` parameter.

## Rollback

Revert the single commit. No destructive change — the migration is
`CREATE OR REPLACE` for the RPC; dropping it cleanly restores the
no-host-promotion state. No data is deleted; existing rooms keep
their current single host.
