## Design decisions (pinned — do not re-decide)

### D1. Per-room opt-in, default OFF — `room_memberships.notifications_enabled`

- New column on `room_memberships`: `notifications_enabled boolean not null default false`.
  Default `false` = a new member gets zero pushes until they opt in.
- Mirror the existing `member_drowning_opt_in` pattern (migration 044/045) exactly:
  - RPC `set_notifications_enabled(p_room_id uuid, p_enabled boolean)` returns void,
    `security definer`, updates only the caller's own membership row
    (`user_id = current_user_id()`).
  - `get_my_rooms` redefined to add `notifications_enabled boolean` via
    `coalesce(m.notifications_enabled, false)`. (get_my_rooms already redefined in
    migration 052; redefine again here with the new column.)
- `get_room_members` (migration 059 shape) redefined to also return
  `notifications_enabled boolean` from the membership row, so the roster carries
  per-member opt-in for the trio fan-out.

### D2. Event mute, per-event — `event_rsvps.notifications_muted`

- New column on `event_rsvps`: `notifications_muted boolean not null default false`.
  Per-event, per-member. Does NOT touch the room's `notifications_enabled`.
- RPC `set_event_notifications_muted(p_event_id uuid, p_muted boolean)` returns void,
  `security definer`. Upserts the caller's own `event_rsvps` row for that event
  (insert with state 'unclaimed' + notifications_muted = p_muted if absent, else
  update). Room scope derives from the event (F-IDENT-01). RLS on event_rsvps already
  lets a member update their own row; the RPC keeps the contract explicit.
- `get_event_rsvps` (migration 047 shape) redefined to also return
  `notifications_muted boolean`, so the service can derive muted member ids from the
  existing `eventRSVPsByEvent` cache.

### D3. Resolve the audit's on-create / host-pinned tension

Item 2 (hard) says: on-create may only reach members who opted into that room's
notifications AND have not declined. Item 4 says host-pinned events "may reach
opted-out members." There is **no pinning model** in the schema — every event is
host-created. The audit's "host-pinned" is a future concept with no schema.

**Decision: the hard requirement (item 2) wins.** The on-create push reaches only
opted-in, non-declined, non-muted members. The one-tap-to-mute (item 4) is a general
per-event escape hatch available to any member who received a push — it is not gated
behind a pinning concept that does not exist. This keeps the app quiet-by-default
(the acceptance test) and satisfies item 2 verbatim. The mute affordance is
implemented in full (per-event, persistent, one tap, does not switch the room
preference). Document this deviation in the loop file. If a pinning concept lands
later it can override the opt-out gate with its own mute; today it does not exist.

### D4. Permission prompt off the join path

- Remove `requestNotificationsIfNeeded()` and its call from `JoinRoomSheet.redeem()`.
  Drop `import UserNotifications` from JoinRoomSheet.
- Authorization is requested inside `NotificationDispatcher.requestAuthorizationIfNeeded()`
  (already there, at the top of `scheduleBriefingTrio`/`scheduleCatchUp`). Since those
  are now only reached for opted-in, non-muted members, the prompt surfaces at the
  first moment a member actually needs a logistics push — the night-of need. No
  further change needed in the dispatcher for timing. In-app briefing slot stays the
  fallback (unchanged).

### D5. Cadence / mute gate lives in `scheduleBriefingTrio`

`NotificationDispatcher.scheduleBriefingTrio` gains two params:
`optedInMemberIds: Set<UUID>` and `mutedMemberIds: Set<UUID>` (default `[]`). In the
per-member loop:
- Skip member entirely if `!optedInMemberIds.contains(memberId)` OR
  `mutedMemberIds.contains(memberId)`.
- On-create: schedule only if `state != .declined`.
- T-48h / morning-of: unchanged logic (skip if declined).

`scheduleCatchUp(eventId:)` (joined-late) is called from
`RoomService.scheduleCatchUpIfNeeded` — gate there: only when the current user's
`notificationsEnabled` is true and the event is not muted.

### D6. Models

- `Room`: add `notificationsEnabled: Bool` (CodingKeys `notifications_enabled`,
  decodeIfPresent default false). This is the CURRENT user's own membership opt-in,
  surfaced through `get_my_rooms` — drives the opt-in toggle UI in the BriefingSlot.
- `Member`: add `notificationsEnabled: Bool` (CodingKeys `notifications_enabled`,
  decodeIfPresent default false). From `get_room_members` — drives the roster filter
  when building the trio cadence.
- `EventRSVP`: add `notificationsMuted: Bool` (CodingKeys `notifications_muted`,
  decodeIfPresent default false). From `get_event_rsvps` — drives the per-event mute.

### D7. RoomStore protocol + both impls

- Protocol `RoomStore` gains:
  - `setNotificationsEnabled(roomId: UUID, enabled: Bool) async throws`
  - `setEventNotificationsMuted(eventId: UUID, muted: Bool) async throws`
- `LiveRoomStore`: call `set_notifications_enabled` and `set_event_notifications_muted`
  RPCs. Update `fetchRoomMembers` (already returns `[Member]` — decode now picks up the
  new field), `fetchEventRSVPs` (same). No change to `fetchRooms` (Room decodes new
  field from get_my_rooms).
- `InMemoryRoomStore`: implement the two RPCs against in-memory state. Seed members
  default `notificationsEnabled = false` (already default). Store mute per event in
  the rsvps map.

### D8. RoomService wiring

- `addEvent`: build cadence from roster, but pass `optedInMemberIds` = roster member
  ids where `notificationsEnabled`, and `mutedMemberIds` = [] (new event).
- `upsertEventRSVP`: pass `optedInMemberIds` from roster filter and `mutedMemberIds`
  from `cachedEventRSVPs(eventId:)` filter.
- `setNotificationsEnabled(roomId:enabled:)` → store RPC, then mirror the updated
  Room into the `rooms` cache (same pattern as `setDrowningOptIn`), so the toggle
  re-renders immediately.
- `setEventNotificationsMuted(eventId:muted:)` → store RPC, then update the cached
  `eventRSVPsByEvent` row for the current user so the mute state reflects immediately.
- `scheduleCatchUpIfNeeded(room:)`: gate on `room.notificationsEnabled` before
  scheduling the joined-late catch-up.

### D9. UI

- `BriefingSlot` (RoomDetailView, the "next to the event" surface):
  - Add an opt-in toggle "Remind me about this room's nights" bound to the current
    user's `notificationsEnabled`, wired through `RoomService.setNotificationsEnabled`.
    The toggle is passed in as state + a callback from `RoomDetailView` (which owns
    the room + roomService). Show it in the `.upcoming`/`.claimed`/`.declined` slots
    (the pre-play briefing slot) — not in the in-play/settle slots.
  - Add a one-tap mute for the current event: "Mute this event" / "Unmute" toggle,
    wired through `RoomService.setEventNotificationsMuted`. Show next to the opt-in
    toggle. Muting this event does not touch the room preference.
- `RoomPage.socialProofCaption(for:)`: return `nil` unless the event's `playedAt` is
  **tonight or tomorrow** (Calendar `isDateInToday` / `isDateInTomorrow`). One date
  check. Otherwise keep the existing startedAt==nil gate.

### D10. Awards (soft change) — verify only

The `AwardsCard` already renders ONLY in the `.seasonClose` V0State (RoomDetailView
`state` resolves `.seasonClose` when `currentSeason.status == .ended`). There is no
standing awards card on the quiet room screen, no badge count, no "3 new awards"
nudge (verified by grep). **No code change** — verify + document in the loop file.
Keep drowning private-to-recipient (already correct).

## Do NOT build
- No streaks, no feed, no news, no DMs/chat. None exist; add none.
- No recap/engagement/re-engagement pushes.
- No metric that grows with app time.
- No pinning model, no push-per-event-exception table beyond the mute column.
