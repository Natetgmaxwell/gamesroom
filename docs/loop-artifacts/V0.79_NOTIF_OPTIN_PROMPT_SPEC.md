# V0.79 — Notification Opt-In: One-Time Prompt → Settings (Quiet Surfaces)

## Problem

V0.54/078's two briefing toggles live inside the hero BriefingSlot card
on the main room page — permanent UI clutter for preferences that are
set once and rarely touched again. Worse:

1. **Members have no settings surface.** The room gear is host-only
   (`RoomDetailView.swift:269`), so "put it in settings" has nowhere
   to go for 90% of the room.
2. **The per-event mute toggle is redundant.** Tapping "Can't make it"
   already silences all pushes for that event
   (`NotificationDispatcher.swift:202` skips `.declined` in fan-out).
   Its only unique case: a claimed member who wants silence — rare,
   and servable from settings.
3. **Quiet-by-default is invisible.** With notifications off and no
   prompt ever shown, members never learn the room pushes exist.

The backend machinery (066/078 RPCs, optedInMemberIds/mutedMemberIds
gates) is correct and stays. This is a UI-layer reallocation: same
RPCs, same columns, new surfaces.

## Design — the loop

**Prompt once → answer → it lives in settings forever.** The main
room page shows notification preferences exactly once per member per
room; after any response it moves to settings where it never
distracts again.

### Surface changes

1. **Remove both toggles from BriefingNotificationRow.** The hero
   briefing card carries no notification controls (V0.78's hierarchy
   gate rendered mute only when room opt-in was on; V0.79 removes
   both rows entirely). The BriefingSlot reverts to content-only:
   event info, RSVP buttons, seat claim pills.

2. **One-time prompt on the main room page.** After the room view
   loads and an active event exists, show a compact inline prompt
   (not a sheet — one tap, no friction): bell icon + "Get a nudge
   when Test Room schedules a night?" + two actions:
   - **"Notify me"** → `set_notifications_enabled(roomId, true)` +
     `tick` haptic, prompt dismisses.
   - **"Not now"** → dismisses. Records the prompt as answered.
   - Renders only when: room opt-in is false AND prompt not yet
     answered for this room (UserDefaults
     `notifPromptAnswered.<roomId>`, per-device). No repeat prompts,
     ever — even after re-login/reinstall it stays answered (device
     scope is acceptable; server-side persistence of "answered" is
     YAGNI for now).

3. **Member-visible "Notifications" row in Room settings.** The gear
   becomes member-visible. RoomSettingsSheet gains a top "My
   notifications" section visible to ALL roles:
   - Toggle: "Remind me about this room's nights" — same
     `set_notifications_enabled` RPC, mirrored into cached Room.
   - Per-event mute list — ONLY when room opt-in is ON and an active
     (unsettled) event exists: "Mute 'Event name'" toggle per active
     event, wired to `set_event_notifications_muted`.
   - This is also the host's surface for their own member-perspective
     notifications (host is a member too).

4. **"Can't make it" stays the mute.** No duplicate mute control on
   the briefing card. The declined-exception in the dispatcher
   (`state == .declined → skip`) already delivers the semantics the
     mute toggle was duplicating. Declining = muting, cleanly.

### What does NOT change

- RPCs `set_notifications_enabled` / `set_event_notifications_muted`
  (078 shapes), RLS, columns, dispatcher fan-out gates — untouched.
- The one-time prompt is local-only (UserDefaults). If a member wipes
  the app, they'll see the prompt again — acceptable; the settings
  surface is the durable fallback.
- 066's `get_my_rooms` read surface — the cached Room already carries
  `notificationsEnabled` for both the prompt gate and the settings
  toggle.

## Server

**None.** Pure client slice. (078 fixed the RPCs; this spec is the UI
that finally uses them correctly.)

## Client

New file: `GamesRoom/Views/RoomNotificationPrefs.swift` — two views:

- `RoomNotifPromptCard` — the one-time inline prompt card (bell,
  copy, Notify me / Not now). Self-contained; takes room + callbacks.
- `RoomNotifSettingsSection` — settings section: opt-in toggle +
  conditional per-event mute list (active events only, room opt-in
   gate).

RoomDetailView: remove BriefingNotificationRow usage + its 3 callback
params (`onToggleNotificationsEnabled`, `onToggleEventNotificationsMuted`,
`notificationsEnabled` stays for the prompt card's gate) — BriefingSlot
params shrink by 2; insert `RoomNotifPromptCard` below the switch
state hero card (rendered when `liveRoom.notificationsEnabled == false
&& !promptAnswered`), new `@State` + UserDefaults helpers.

RoomSettingsSheet: add member-visible section via existing
`settingsRow` pattern; gear button host-only → member-visible in
RoomDetailView toolbar (`if isHost` → always).

RoomPage: gear stays host-only there (it opens the same sheet for the
 last-viewed host room; changing its visibility is out of scope — the
 sheet itself now self-gates by role).

## Micro-interactions

- Prompt "Notify me" → `Haptics.tick()`; prompt dismiss on "Not now" —
  no haptic (quiet exit).
- Settings toggle flips → `tick`.
- No new haptics (Layer 0 vocabulary only).

## Decisions locked at spec time

- Prompt: inline card, not sheet. One tap, no modal friction.
- "Not now" still records answered (never re-prompt) — decisiveness
  over re-asking; user can always opt in from settings.
  server-side "answered" persistence: out (YAGNI).
- Per-event mute list in settings shows ACTIVE events only — muted
  history for settled events is trivia nobody needs.
- The gear: member-visible in RoomDetailView toolbar (this slice);
  RoomPage gear stays host-only (scope control).
- Host sees same "My notifications" section (host is a member too).
