# V0.37 — Cold-start session restore (kanban t_ecbcb3d7)

## Context

User feedback: "The app asks me to sign in with Apple every time I open it from a cold start."

Root cause (traced in code):

`ContentView.swift` drives the sign-in sheet with a binding whose getter is
`auth.currentUser == nil`. On cold start `AuthService.currentUser` is `nil`
because it is an in-memory `@Published` property — nothing restores the session
before the view renders. The sheet appears immediately, even though Supabase
has a valid session in the keychain.

`AuthService.loadCurrentUser()` already reads the session from
`SupabaseClientProvider.shared.auth.session` and joins the `public.users` row —
but it is only called after sign-in succeeds (from `SignInView`), never on app
launch. `GamesRoomApp.swift`'s header comment already documents the intended
design ("its `loadCurrentUser()` is called by `ContentView` in its `.task`
modifier on first appearance") — this change makes that documented design true.

## Design decisions (pinned)

1. **Restore point**: `ContentView` root `.task` — fires once on first
   appearance, runs on MainActor. Not `GamesRoomApp.init` (app launch must stay
   synchronous per the existing comment).
2. **Loading state**: new `@State private var isRestoringSession = true`. The
   root body branches: splash while restoring, `TabView` otherwise. Splash is
   `Theme.Palette.background` + `ProgressView()` — no new file, no new tokens,
   no hardcoded colors. Dark scheme is already forced at the root by
   `GamesRoomApp`.
3. **Sheet binding** accounts for the restore window:
   `get: { isRestoringSession ? false : auth.currentUser == nil }` — no sheet
   during restore, sheet only when restore finished without a user.
4. **No `AuthService` changes.** `loadCurrentUser()` keeps its collapse-to-nil
   semantics. Known limitation (pre-existing, unchanged): with a valid keychain
   session but no network, the `public.users` fetch fails and the sign-in sheet
   still appears. Out of scope for this card.
5. **No new Swift files, no pbxproj change, no migration.** Pure client-side
   view change.
6. **Parse gate coverage**: `scripts/parse-check-swiftui.sh` currently scans
   `GamesRoom/Views`, `GamesRoom/Services`, `GamesRoomWidgets`,
   `GamesRoomWatch` — NOT the repo-root files. The changed file
   (`GamesRoom/ContentView.swift`) is not gated today. Extend the scan to
   `GamesRoom -maxdepth 1` (covers `ContentView.swift` + `GamesRoomApp.swift`).
   `swiftc -parse` is syntax-only, so the `Supabase` import in ContentView does
   not need to resolve.

## Acceptance criteria (from the card)

- Cold start with a valid Supabase session skips the sign-in sheet.
- Cold start with NO valid session shows the sign-in sheet (existing behavior
  preserved).
- Brief loading state during session check — no flash of sign-in.
- Tests + parse-checks green.

## Files that may change (exactly these four)

- `GamesRoom/ContentView.swift` — the fix
- `scripts/parse-check-swiftui.sh` — gate coverage for the changed file
- `docs/loop-artifacts/V0.37_SESSION_RESTORE_SPEC.md` — this file
- `docs/loop-artifacts/.v0.37_session_restore_loop.md` — loop contract

Do NOT touch: `AuthService.swift`, `SignInView.swift`, `GamesRoomApp.swift`
(comment already accurate once the fix lands), `Theme.swift`, pbxproj,
migrations, any other Swift file.

## Testing note

The Foundation runner (`main.swift` + `build-and-run-tests.sh`) compiles
Models/ + Packs/ only and cannot cover SwiftUI view logic (repo convention,
V0.36 loop rule 3). This change is view-layer; no new runner tests are
possible or expected. "Tests + parse-checks green" = the existing suite stays
green and the changed files pass the extended parse gate.
