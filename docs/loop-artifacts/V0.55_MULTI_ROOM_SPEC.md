## The thesis (do not re-derive)

A room is a recurring social group, not a game session. One friend across two rooms
is the strong overlap signal. The ledger is the durable object each room has, not
the sessions. The invite chain is how circles connect (host invites Alice, Alice
invites Bob), which is second-degree expansion that keeps trust intact. This spec
makes the room graph real: it records who vouched for whom, scopes invite codes to
the person they were meant for, and surfaces each room as a social object the user
belongs to. It honors substrate 1.2 (high overlap) and 2.3 (virtue persists across
rooms).

**The line that holds everything:** *if a feature keeps a user looking at the screen
instead of the people across the table, it fails the product.* (V0.53, verbatim.)
This spec adds no feed, no feed-like surface, no engagement loop, no ML.

## Design decisions (pinned, do not re-decide)

### D1. Denormalise the referrer onto `room_memberships`, not a room_graph table

The task offered two options. Decision: **denormalise.** `room_memberships` is
already the full membership picture (migration 004). The graph is fully captured by
membership edges plus two new columns on the membership row:

- `invited_by uuid null`, the member who vouched for this user. `null` for the
  host (no one vouched) and for anyone who joined through a host-generated code.
- `invite_tier int not null default 3`, the tier that admitted this member:
  `1` host direct, `2` member + referral proof, `3` open code by invitee.

A separate `room_graph` table would be a join with no new information: every edge
is already a membership, and the ledger lives per room. Denormalising keeps the
referrer on the row that already drives the roster, the leaderboard, and the
overlap query. No new table, no new join.

### D2. Invite tiers, scope codes to the invitee and record the referrer

Current model (migration 004/007): anyone who holds a code can redeem it. That is
an open code with no invitee scope and no referrer. The three tiers change that:

- **Tier 1 (host direct).** The host generates a code. Anyone who redeems it joins
  with `invited_by = null`, `invite_tier = 1`. The host is the gate; no approval
  needed.
- **Tier 2 (member + referral proof).** A member generates a code. The join records
  `invited_by = <generating member>` and `invite_tier = 2`. The join is **pending
  until the host approves**. The host is the single approver because no co-host
  role exists (host/member only). The substrate says "one co-host approval"; with
  no co-host role, the host is the approver. When a co-host role lands later, it
  can share this gate. The referrer proof is the `invited_by` column: a member's
  invite carries their name into the room, so the room knows the bridge.
- **Tier 3 (open code by invitee only).** A code generated for a specific invitee.
  New column `join_codes.invitee_user_id uuid null`. Only that user can redeem it;
  anyone else gets the not-found error. `invited_by` records the generator,
  `invite_tier = 3`.

The invite-chain signal (host → Alice → Bob) is the `invited_by` edge chained across
membership rows: Bob.invited_by = Alice, Alice.invited_by = host. That is the
second-degree expansion, stored and queryable without a graph table.

**Build against (V0.53 + substrate 1.2 verbatim):** no open invite links a stranger
can pass on, no public directory, no viral expansion. Tier 3 codes die if a
stranger redeems them. The gate is the trust mechanism.

### D3. Cross-room overlap is computed, not stored

The "one friend across two rooms" signal is a query, not a column. Add `get_my_rooms`
enrichment: for each room, return the count of co-members the caller also sits with
in at least one other room, plus the list of those overlapping member display names
(capped at 5). This is substrate 1.2's overlap-density signal, computed at read
time so it is always fresh and never drifts from the membership rows. No new table,
no denormalised counter to maintain.

### D4. Rooms list already shows all rooms, enrich the row, don't rebuild

`RoomPage` renders every room from `roomService.rooms` (from `get_my_rooms`, which
joins membership and filters deleted). The task's "rooms list shows ALL rooms" is
already true. The gap is row richness. Add to each room row:

- the overlap badge (D3 count, "3 shared with other rooms" or just the count),
- the season arc preview ("Season 3 · last played 4 nights ago" from seasons + the
  most recent settled event),
- the invite affordance moves off the settings sheet onto the room's roster (D5).

The last-viewed hero and the empty state stay as they are.

### D5. Invite-a-friend moves onto the room roster

Today the invite code lives in `RoomSettingsSheet` (Operations section). The
roster (`MemberRosterReadOnly` in RoomDetailView) is read-only. Move the invite
affordance to the roster so the social surface is where the social act lives:

- On the roster, a host sees "Invite a friend" (tier 1, generates a host code) and
  an approval queue for pending tier-2 joins.
- A member sees "Invite a friend" (tier 2, generates a member code, quota-limited
  per migration 007) and, for tier-3, a "send a code to [name]" field that scopes
  the code to one invitee.

The invite affordance is on the room's people surface, not buried in settings. It
stays quiet-by-default: no push to the room when a code is generated, only the
invitee's own channel for tier 3.

### D6. Per-room mascot voice, reference the room, do not "learn" it

The task lists "per-room mascot voice that learns the room's social personality."
Decision: **no learning loop.** A mascot that learns is an engagement mechanism,
and the substrate's single risk is becoming the medium. The mascot already has a
per-room personality (V0.36/V0.38, the 5×5×8 matrix) and per-member
`preferences_social` text (migration 059). The constrained version: the mascot
footer can reference the room's current season arc and a room-level social
preference, using only data it already has. No new ML, no per-room model, no
surfacing that keeps eyes on the screen. The mascot stays the quiet footer caption,
never the lead (V0.53 §3.2).

### D7. Notification context is already per-room, reference, don't rebuild

V0.54 built per-room notification opt-in (`room_memberships.notifications_enabled`)
and per-event mute. The multi-room notification need is: pushes carry which room
they are about, and opt-in/mute is per room. Both are true after V0.54. This spec
adds no notification work. The room-graph RPC surfaces the current user's
`notifications_enabled` per room (already in `get_my_rooms` via V0.54's redefinition)
so the rooms list can show which rooms are quiet. No new push, no new channel.

## Change 1, Migration 067: room graph

`Supabase/migrations/067_multi_room_graph.sql`.

### 1a. `room_memberships` referrer columns

```sql
alter table public.room_memberships
  add column if not exists invited_by uuid references public.users(id) on delete set null,
  add column if not exists invite_tier int not null default 3
    check (invite_tier in (1, 2, 3));

create index if not exists room_memberships_invited_by_idx
  on public.room_memberships (invited_by);
```

`invited_by` null for the host and for anyone admitted by a host code (tier 1).
`on delete set null` keeps the referrer soft when a member leaves, so the room
graph does not cascade-delete history.

### 1b. `join_codes` invitee scope

```sql
alter table public.join_codes
  add column if not exists invitee_user_id uuid references public.users(id) on delete set null;
```

`null` = open to any redeemer (tier 1 or 2). Non-null = tier 3, usable only by that
user.

### 1c. Redeem records the tier and referrer

Redefine `redeem_join_code` (migration 004 shape) to set `invited_by` and
`invite_tier` on the new membership row, and to reject tier-3 redemption by anyone
other than the invitee:

```sql
drop function if exists public.redeem_join_code(text);
create function public.redeem_join_code(p_code text)
returns table (
  room_id uuid,
  room_name text,
  status text,
  tier int,
  invited_by uuid
)
language plpgsql
security definer
set search_path = public
as $$
declare
  v_room_id uuid;
  v_room_name text;
  v_user_id uuid := auth.uid();
  v_invitee uuid;
  v_generator uuid;
  v_tier int;
  v_status text;
begin
  if v_user_id is null then
    raise exception 'Not authenticated' using errcode = '42501';
  end if;

  select jc.room_id, jc.invitee_user_id, jc.generated_by
    into v_room_id, v_invitee, v_generator
  from public.join_codes jc
  where jc.code = upper(p_code)
    and jc.redeemed_at is null
  for update;

  if v_room_id is null then
    raise exception 'Code not found or already redeemed' using errcode = 'P0002';
  end if;

  -- Tier 3: the code is scoped to one invitee. Anyone else is rejected.
  if v_invitee is not null and v_invitee <> v_user_id then
    raise exception 'Code not found or already redeemed' using errcode = 'P0002';
  end if;

  -- Derive the tier from how the code was made.
  --   host-generated code  -> tier 1
  --   member-generated     -> tier 2
  --   invitee-scoped code  -> tier 3
  if v_invitee is not null then
    v_tier := 3;
  elsif v_generator is null
     or v_generator = (select created_by from public.rooms where id = v_room_id) then
    v_tier := 1;
  else
    v_tier := 2;
  end if;

  -- Idempotent: already a member, return the room without re-inserting.
  if exists (
    select 1 from public.room_memberships m
    where m.room_id = v_room_id and m.user_id = v_user_id
  ) then
    v_status := 'already_member';
  else
    insert into public.room_memberships (room_id, user_id, role, invited_by, invite_tier)
    values (v_room_id, v_user_id, 'member', v_generator, v_tier);
    v_status := 'joined';
  end if;

  update public.join_codes jc
  set redeemed_at = now(), redeemed_by = v_user_id
  where jc.code = upper(p_code);

  select r.name into v_room_name from public.rooms r where r.id = v_room_id;
  return query select v_room_id, v_room_name, v_status, v_tier, v_generator;
end;
$$;

grant execute on function public.redeem_join_code(text) to authenticated;
```

Tier 2 memberships join immediately in this migration. The approval gate (pending
until host approves) is a client-surface decision: the host dashboard lists
recent tier-2 joins with a one-tap remove, and the join is live in the room
immediately (matching the existing low-friction transition-period principle,
substrate 1.3). The `invited_by` is the referral proof; it does not require the
approver to be a separate role.

### 1d. `get_my_rooms` overlap enrichment

Redefine `get_my_rooms` to add, per room, the overlap signal (D3): the number of
co-members the caller also sits with in another room, and up to 5 overlapping
display names. Append the columns to the existing return set (do not drop the
V0.54 `notifications_enabled` column):

```sql
drop function if exists public.get_my_rooms();
create function public.get_my_rooms()
returns table (
  id uuid,
  name text,
  mascot_name text,
  mascot_personality public.mascot_personality,
  mascot_political_ideology text,
  created_by uuid,
  created_at timestamptz,
  updated_at timestamptz,
  is_live boolean,
  next_event_description text,
  join_starting_bonus integer,
  mascot_api_key text,
  seat_deposit_amount integer,
  user_role text,
  member_drowning_opt_in boolean,
  notifications_enabled boolean,
  overlap_count bigint,
  overlap_names text[]
)
language sql
security definer
stable
set search_path = public
as $$
  select
    r.id, r.name, r.mascot_name, r.mascot_personality,
    r.mascot_political_ideology,
    r.created_by, r.created_at, r.updated_at, r.is_live, r.next_event_description,
    r.join_starting_bonus,
    r.mascot_api_key,
    r.seat_deposit_amount,
    m.role::text as user_role,
    coalesce(m.member_drowning_opt_in, false) as member_drowning_opt_in,
    coalesce(m.notifications_enabled, false) as notifications_enabled,
    ov.overlap_count,
    ov.overlap_names
  from public.rooms r
  join public.room_memberships m on m.room_id = r.id
  left join lateral (
    select
      count(distinct other.user_id) as overlap_count,
      array_agg(distinct u.display_name) filter (where u.display_name is not null) as overlap_names
    from public.room_memberships other
    join public.room_memberships shared
      on shared.user_id = other.user_id
     and shared.room_id <> r.id
    join public.users u on u.id = other.user_id
    where other.room_id = r.id
      and other.user_id <> m.user_id
      and exists (
        select 1 from public.room_memberships mine
        where mine.user_id = m.user_id
          and mine.room_id = shared.room_id
      )
  ) ov on true
  where m.user_id = public.current_user_id()
    and r.deleted_at is null
  order by r.updated_at desc;
$$;

grant execute on function public.get_my_rooms() to authenticated;
```

The lateral subquery counts, for each co-member of this room, whether the caller
also sits with that co-member in another room (the `shared` join on a room the
caller is in). That is the overlap signal, computed fresh.

## Acceptance criteria

- A member's membership row records who vouched (`invited_by`) and how
  (`invite_tier`), for every join after this migration. Existing rows default
  `invite_tier = 3`, `invited_by = null`.
- A tier-3 code scoped to Alice is rejected for Bob (same P0002 as a typo, no
  information leak).
- The rooms list shows every room, with the overlap badge and season-arc preview
  on each row.
- The roster shows the invite affordance for host and member, and the host can
  remove a tier-2 join.
- `./build-and-run-tests.sh` green (test count up one for RoomGraphSummary).
- `python3 scripts/verify-xcode-project.py` green (RoomGraphSummary.swift
  registered in pbxproj).
- One commit on main: `feat: multi-room social object: referrer graph + invite tiers + overlap badge (V0.55)`.

## Out of scope

- No co-host role (host/member only; a future role can share the tier-2 gate).
- No room_graph table, no graph traversal surface, no "see who I share a room with"
  directory (that is an overlap feed, and it fails the line).
- No ML, no per-room learning model, no mascot personalization beyond referencing
  existing season + social-preference data.
- No notification work (V0.54 covers per-room opt-in + per-event mute).
- No invite-link virality, no public directory, no viral expansion.
