# V0.94 — per-event hidden members (replaces per-room blacklist)

## Problem

V0.12's `room_blacklist` table (migration 022) is a per-room list of users
the host can pre-emptively block from joining. The feature was never
finished on live: `redeem_join_code` doesn't check it, the briefing
read RPCs don't filter by it, and Connor-style "I have hostilities in
the room" never worked as advertised.

The actual product need is narrower: when a host creates an event, the
host should be able to mark a small set of members who **don't see this
event and don't receive any push for it**. No membership-level effects,
no read-side data leakage for the rest of the room — just "this event
is invisible to these people."

## What we're shipping

A per-event `events.hidden_from_user_ids uuid[]` column. The host
passes the list at event-create time (host-only edit; we don't expose a
"reveal later" path for V0.94).

Three behaviors must follow from the column:

1. The hidden members don't see the event in the briefing or
   `get_active_event`.
2. The hidden members don't see the event's RSVP roster
   (`get_event_rsvps`).
3. The hidden members don't receive a briefing push for the event.
   The realtime path (V0.77) self-schedules; it reads the event row
   server-side, so adding a `WHERE NOT (auth.uid() = ANY(hidden_from_user_ids))`
   to the briefing RPCs is enough — the realtime path checks the
   server-visible event row and skips hidden members.

The hidden members are still room members. They see the room, can
chat in any non-hidden event, can claim RSVPs on other events. Only
this one event (and its RSVPs) is invisible to them.

## What we're removing

- The `public.room_blacklist` table (migration 022).
- The 3 per-room blacklist RPCs: `add_to_blacklist`,
  `remove_from_blacklist`, `get_room_blacklist`.
- The `p_blacklisted_user_ids` parameter on the `create_room` RPC.
- The `blacklistedUserIds: [UUID]` parameter on the iOS
  `RoomService.createRoom` and `RoomStore.createRoom` methods.

These are not used anywhere except the iOS `createRoom` plumbing
(which the iOS code passes `[]` to in every call site — see
`main.swift:1692` and the in-memory store at
`InMemoryRoomStore.swift:562`). No production feature depends on the
per-room data path. Drop is safe.

## Schema

```sql
-- Migration 090
alter table public.events
  add column if not exists hidden_from_user_ids uuid[] not null default '{}'::uuid[];

-- Index for the RLS join below (gin on the array).
create index if not exists events_hidden_from_user_ids_gin
  on public.events using gin (hidden_from_user_ids);

-- Drop the per-room feature entirely.
drop policy if exists "Host reads blacklist" on public.room_blacklist;
drop policy if exists "Host writes blacklist" on public.room_blacklist;
drop table if exists public.room_blacklist;

drop function if exists public.add_to_blacklist(uuid, uuid);
drop function if exists public.remove_from_blacklist(uuid, uuid);

-- create_room loses its p_blacklisted_user_ids parameter.
create or replace function public.create_room(
    p_name text, p_mascot_name text, p_mascot_personality text,
    p_mascot_political_ideology text, p_join_starting_bonus integer default 200,
    p_mascot_api_key text default null::text
)
returns uuid language plpgsql security definer set search_path = public as $$
-- ... existing body, with the room_blacklist INSERT block removed ...
$$;

-- add_event grows a hidden_from_user_ids parameter.
create or replace function public.add_event(
    p_room_id uuid, p_name text, p_played_at timestamptz, p_pack_slug text,
    p_hidden_from_user_ids uuid[] default '{}'::uuid[]

-- ... existing body + insert into events (... hidden_from_user_ids) ...
```

## RLS rewrites

```sql
-- members can read events — REWRITTEN to honor hidden_from_user_ids.
-- A hidden user returns 0 rows for that event.
create policy "members can read events"
  on public.events for select using (
    exists (
      select 1 from public.room_memberships m
      where m.room_id = events.room_id
        and m.user_id = public.current_user_id()
    )
    and not (public.current_user_id() = any(events.hidden_from_user_ids))
  );

-- The RLS on event_rsvps currently uses `events` to gate. We make
-- the same hidden-from check via the same join.
-- (Re-state the existing policy with the additional NOT IN clause.)
```

We do **not** change the RLS on `events` for INSERT/UPDATE/DELETE
(those are host-only paths). We do **not** touch `settlement_attestations`
or the casino flow — those are event-scoped reads but the user said
the spec is "can't see the event or get the push," not "can't see
everything that touches the event." A hidden user can still see their
own attestations if they navigate to the session by some other path
(they currently can't, but if the briefing redirects them to the
session, the session screen should also be guarded — we address that
in iOS, not in DB RLS, since RLS on `settlement_attestations` would
break the host's view of disputes).

## Push-side behavior

`RealtimeEventService.handleEventInsert` (Swift) reads the event row
to schedule the briefing trio. It currently checks
`room.notificationsEnabled` but not the hidden list. After V0.94, it
must read `event.hiddenFromUserIds` and skip any local user that
matches. The schedule call is a per-user scheduling call, so the
simplest path: pass `optedInMemberIds: [callerId: .unclaimed]`
but the room-level filter already restricts to caller — we additionally
check `if event.hiddenFromUserIds.contains(callerId) { return }` at
the top of `handleEventInsert`.

The same check applies to the V0.91 catch-up path
(`scheduleActiveEventOnCreateIfMissing`): skip if caller is in
`hiddenFromUserIds`.

## iOS surface changes

1. Drop `blacklistedUserIds` parameter from:
   - `RoomStoreProtocol.createRoom`
   - `RoomService.createRoom`
   - `RoomStore.createRoom` (REST + parameter)
   - `InMemoryRoomStore.createRoom`
   - `main.swift` test fixture

2. Add `hiddenFromUserIds: [UUID] = []` to:
   - `RoomStoreProtocol.addEvent`
   - `RoomService.addEvent`
   - `RoomStore.addEvent` (REST + parameter)
   - `InMemoryRoomStore.addEvent`

3. `Event` model gains a `hiddenFromUserIds: [UUID]?` field, decoded
   from `hidden_from_user_ids`.

4. `AddEventSheet` adds a "Hidden from" chip row that opens a member
   picker. Empty by default; existing events are unaffected.

5. `RealtimeEventService.handleEventInsert` short-circuits if the
   caller is in `event.hiddenFromUserIds`.

6. `RoomService.scheduleActiveEventOnCreateIfMissing` checks the
   same.

## Verification

Behavioral probe (BEGIN...ROLLBACK impersonation):

- Create a room. Have Nathan + Connor as members.
- Add event A. Add event B with `hidden_from_user_ids = [Connor]`.
- As Connor: `get_active_event(room)` for room returns the most-recent
  of A or B. If A was created last, returns A. If B was created last,
  returns NULL (B is hidden, A is older — but the most recent is
  B, which is hidden, so the function needs a tie-breaker: "the
  most recent non-hidden event"). The current implementation
  returns the most recent event period; per-event hiding is a
  display-layer concern, not a SQL-layer "most recent" change. We
  expose a host-only `get_active_event_for_member` variant that
  takes `p_viewer uuid` and filters. The iOS client passes the
  caller's user id explicitly.
- As Connor: `get_briefing_summary(event_b)` returns 0 rows.
- As Connor: `get_event_rsvps(event_b)` returns 0 rows.
- As Nathan (host, not hidden on B): both events visible, both
  briefings visible, both RSVPs visible.
- As Nathan (host, hidden on event A): A not visible, B visible.

The probe runs through all 6 assertions and asserts pass on the 5
that should pass, fail on the 1 that should fail (probe bug check).

## Rollback

Drop migration 091 (reverse of 090):
- Drop `events.hidden_from_user_ids` column + index.
- Revert RLS policy on `events` to the pre-V0.94 form.
- Revert `create_room` and `add_event` signatures.
- Re-add `room_blacklist` table + the 3 per-room RPCs (from migration
  022).
- Re-add `blacklistedUserIds` to iOS.

The iOS rollback is the only one that takes any wall-clock time; the
DB rollback is mechanical.

## Out of scope (V0.94 deliberately does NOT do these)

- **Multi-host promotion.** Different feature, different scope, spec
  pending.
- **Per-room blacklist resurrection** as a separate feature. If the
  user wants "never let this person into the room," that's a future
  spec — and would re-introduce the `room_blacklist` table with
  its own membership-creation gate.
- **Editing `hidden_from_user_ids` after the event is created.** V0.94
  is create-time only. If the host wants to add someone mid-week,
  they delete + recreate the event.
- **Revealing a hidden event to a specific user.** Out of scope.
