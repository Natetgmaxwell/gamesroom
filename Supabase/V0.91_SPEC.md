# V0.91 — Late-opt-in catch-up for event-created briefing pushes

## Problem

V0.54 made notifications quiet-by-default (`room_memberships.notifications_enabled` defaults to `false`). The realtime INSERT path (`RealtimeEventService.handleEventInsert:128`) hard-returns on `room.notificationsEnabled == false`. Result: when a member's flag is `false` at the moment an event is created, the device receives the realtime notification but skips scheduling. If the member flips their flag on later (via the V0.79 opt-in prompt or the settings toggle), no catch-up fires — they never receive the briefing they missed.

Verified case: Felt Faction room (Felt Faction `0188773c-...`), Connor joined 10:28 UTC, event "Test Room" created 10:34 UTC while Connor's flag was `false`, Connor flipped the flag at 11:03 UTC. The realtime path was gated out at 10:34 and no subsequent catch-up fired.

## Fix

Two idempotent scheduling call sites on top of the existing realtime path:

1. **Opt-in flip** — `RoomService.setNotificationsEnabled(_, enabled: true)` schedules the on-create push for the room's active event after the cache mirror.
2. **Room-open** — `RoomDetailView.loadActiveIfNeeded` schedules the same after a fresh `loadActiveEvent`.

Both call sites route through a single new public method, `RoomService.scheduleActiveEventOnCreateIfMissing(roomId:)`, which gates on `room.notificationsEnabled`, the presence of an active event, and `NotificationDispatcher.hasPendingOnCreate(eventId:userId:)`. The dispatcher's stable `(eventId, kind, userId)` identifier means whichever path wins, the loser is a no-op overwrite — no double-fire possible.

A new `NotificationDispatcher.hasPendingOnCreate(eventId:userId:)` exposes the duplicate-check so both call sites use the same predicate.

## What it does NOT cover (accepted gaps, same as V0.77)

- Device-suspended / offline at the moment of event creation is partially covered (room-open path) but not guaranteed for users who never reopen the room.
- APNs-driven remote push is a V0.8+ slice, not in scope here.
- A realtime UPDATE stream on `room_memberships` was considered and rejected: the only writer of `notifications_enabled` is the local user's own RPC, so the local write path covers every case without needing a publication-side change or `REPLICA IDENTITY FULL`.

## Verification

1. `xcodebuild ... build` is green.
2. Manual end-to-end on simulator: a second device opted-out at event-create time, opts in later, opens the room → briefing push arrives.
3. Idempotency probe (pending): the iOS side's `hasPendingOnCreate` check is sufficient; the suite doesn't have a Swift-side push-queue test harness today.

## Rollback

Revert the single commit. No DB migration, no schema change, no migration file. Pure client-side change.
